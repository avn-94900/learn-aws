# 📘 AWS & Cloud Interview Notes (For Java Backend Microservices Developer)

---

## 🔹 Core AWS Services

### 1. **EC2**

* **What is EC2?**
  Elastic Compute Cloud, provides resizable compute capacity (VMs) in AWS.
* **Instance types?**

  * General purpose (t2, t3, m5)
  * Compute optimized (c5, c6g)
  * Memory optimized (r5, x1e)
  * Storage optimized (i3, d2)
  * Accelerated computing (p3, g4 for ML/AI)
* **Why EC2 over other compute?**
  When full control of OS, networking, storage is needed (e.g., running custom middleware, legacy apps).
* **Multiple apps in one EC2?**
  Yes, but not best practice in microservices → leads to tight coupling, scaling challenges. Use containers/ECS/EKS instead.
* **Storage types in EC2?**

  * Instance Store (ephemeral, lost on stop/terminate)
  * EBS (persistent block storage)
  * EFS (shared NFS-like file system, scalable)
  * S3 (object storage, not directly mounted but used for static files/backup).

---

### 2. **S3**

* **Purpose:** Object storage for static files, backups, logs, images, etc.
* **Difference from RDBMS:**

  * S3 is object storage (files, blobs, metadata)
  * RDBMS is structured, relational, transactional.
* **Best practices:**

  * Enable versioning & lifecycle policies
  * Apply encryption (SSE-S3, SSE-KMS)
  * Block public access by default
  * Use S3 bucket policies + IAM for access
  * Use CloudFront for CDN distribution.

---

### 3. **SQS vs Kafka**

* **SQS:**

  * Fully managed queue service
  * Simple, reliable, scalable
  * Point-to-point messaging
  * At-least-once delivery
  * Cheaper, no infra management
  * Use cases → async job processing, decoupling microservices.
* **Kafka (MSK in AWS):**

  * Distributed event streaming platform
  * Pub-sub model, retains events for configurable time
  * High throughput, real-time analytics
  * Use cases → event sourcing, data pipelines, stream processing.
* **When to choose?**

  * SQS → simple decoupling, low throughput
  * Kafka → event streaming, replayability, high scale.

---

### 4. **ECS & Fargate**

* **ECS Setup requirements:**

  * Task Definitions (Docker containers)
  * Services (long-running tasks)
  * Cluster (EC2 or Fargate launch type).
* **Launch types:**

  * **EC2 launch type:** You manage EC2 instances.
  * **Fargate launch type:** Serverless, AWS manages infra.
* **When to use Fargate?**

  * Small workloads, unpredictable scaling, no infra mgmt.
* **When to use ECS-EC2?**

  * Large workloads with steady usage → cheaper if EC2 reserved.

---

### 5. **Lambda**

* **Use cases vs EC2/Fargate:**

  * Lambda → event-driven, short-lived (up to 15 min).
  * EC2/Fargate → long-running workloads, custom infra.
* **Cost:**

  * Lambda → pay per execution & duration.
  * EC2 → pay per running instance.
  * Fargate → pay per vCPU & memory.
* **Best for:**
  Lightweight functions, API integration, file processing, scheduled jobs.

---

### 6. **Networking**

* **NACL vs Security Groups:**

  * **SG:** Stateful firewall at instance level (allows inbound + auto allows response).
  * **NACL:** Stateless firewall at subnet level (need explicit inbound/outbound rules).
* **Two-tier architecture:**

  * Web tier (public subnet + ALB)
  * App/DB tier (private subnet, SG restricted).

---

### 7. **Authentication & Authorization**

* IAM Users, Roles, Groups.
* Fine-grained policies using JSON.
* AssumeRole for cross-account.
* Cognito for app authentication.
* API Gateway + Lambda Authorizers for token-based auth.

---

## 🔹 Advanced AWS

### 8. **Migration**

* **Best practices (Monolith → Microservices):**

  * Strangler pattern (gradual migration)
  * Use API Gateway to route traffic
  * Containerize apps (ECS/EKS)
  * Break DB into smaller schemas.

---

### 9. **API Gateway**

* Purpose → Managed API front door, routing, authentication, throttling, caching.
* Integrates with Lambda, ECS, backend services.

---

### 10. **Autoscaling**

* Horizontal scaling of EC2, ECS, Lambda.
* Based on CloudWatch metrics (CPU, memory, custom).
* Predictive scaling + spot instances for cost optimization.

---

### 11. **Data Transfer**

* **DataSync:** Managed service for copying large datasets between on-prem/AZ/regions.
* Alternatives: S3 Transfer Acceleration, Snowball, S3 batch operations.

---

### 12. **Monitoring & Logging**

* **Prometheus:** Collects metrics (ECS, EKS integration).
* **Custom metrics:** Export JVM metrics (GC, heap usage) using Micrometer.
* **Splunk / CloudWatch Logs:** Centralized log storage & search.
* **X-Ray:** Distributed tracing for microservices.

---

### 13. **Infra Management**

* **Terraform:**

  * IaC (Infrastructure as Code)
  * Supports multi-cloud
  * Modular, version-controlled infra
  * Example: Define ECS service + ALB + TargetGroup in Terraform.

---

### 14. **CI/CD**

* **Flow (commit → deploy):**
  Developer → GitHub/GitLab → CodePipeline/Jenkins → Build (Maven, CodeBuild) → Test → Deploy (CodeDeploy/ECS).
* **Pre-production checks:**

  * Canary deployments
  * Automated integration tests
  * Load testing.
* **Deployment strategies:**

  * Rolling update
  * Blue/Green
  * Canary release.
* **Debugging slowness:**

  * CloudWatch metrics (CPU, memory, latency)
  * X-Ray for tracing
  * Profiling JVM with Flight Recorder.
