## 2. Networking in AWS

### a) VPN vs VPC

* **Virtual Private Network (VPN):**

  * Securely connects your on-premises network to AWS cloud via the internet.
  * Used for hybrid cloud setups.

* **Virtual Private Cloud (VPC):**

  * A logically isolated section of the AWS cloud where you define your own **networking setup**.
  * You control **IP ranges, subnets, routing, NAT, security groups**.
  * **Why used?** For better **security, control, and network segmentation**.

**VPC Communication:**

* Within VPC: Components (EC2, RDS, Lambda, Load Balancer) communicate via private IPs.
* Across VPC: Use **VPC Peering**, **Transit Gateway**, or **VPN**.

### b) Subnet

* A **subdivision of VPC’s IP range**.
* Types:

  * **Public Subnet:** Direct access to internet via Internet Gateway.
  * **Private Subnet:** No direct internet; used for DBs, internal services.
* **Why needed?** For **isolation** (web servers in public subnet, DBs in private subnet).

# 📘 AWS Notes

## 1️⃣ Amazon SQS (Simple Queue Service)

**Definition**:
Fully managed message queuing service that decouples microservices and ensures asynchronous communication.

**Advantages**

* Decouples services → no blocking, no freezing under load.
* Smoothly handles high traffic.
* Reliable, scalable, fault-tolerant.
* Removes tight coupling → easier scaling.

**Without SQS (tightly coupled)**

* Services wait for responses (blocking).
* Users may freeze due to slow responses.
* Hard to scale.
* Risk of crashes under heavy load.

**With SQS (loosely coupled)**

* Services don’t block.
* Lost connections handled gracefully.
* Scales automatically under heavy load.

**Classifications**:

* **Standard Queue**

  * Unlimited throughput.
  * At-least-once delivery.
  * Best-effort ordering.
* **FIFO Queue**

  * Exactly-once processing.
  * Strict ordering.
  * Limited throughput compared to Standard.

# ⚡ **AWS Lambda (Serverless Compute)**

🔹 **Why VPC?**

* Control traffic flow with **Security Groups + NACLs**.
* Integration with on-premises via **VPN/Direct Connect**.

🔹 **Default VPC:** AWS creates one per region → you can launch resources without custom setup.
🔹 **Custom VPC:** For production → you define subnets, routing, gateways.

📌 Example:

* **Web Tier (Public Subnet)** → accessible by internet via Load Balancer.
* **App/DB Tier (Private Subnet)** → not exposed, only accessible internally.

# ⚖️ **Load Balancers in AWS (ELB family)**

👉 Distribute traffic across multiple servers for **scalability + fault tolerance**.

* **ALB (Application Load Balancer)** → HTTP/HTTPS (Layer 7), routing by URL/host headers.
* **NLB (Network Load Balancer)** → TCP/UDP (Layer 4), high-performance, millions of requests/sec.
* **CLB (Classic Load Balancer)** → Old gen, basic Layer 4/7.
* **GWLB (Gateway Load Balancer)** → Route traffic through 3rd-party firewalls/security appliances.

📌 Example:

* Website traffic → **ALB** routes requests to EC2 in multiple AZs.
* Gaming app (low latency TCP) → **NLB**.

# 🌍 **Route 53 (DNS Service)**

👉 AWS’s **DNS + traffic routing service**.

🔹 **Why used?**

* Converts domain name → IP.
* Provides **global traffic management** (latency-based, failover, geo-routing).

🔹 **Not per AZ** → **Route 53 is global**, not tied to one AZ.

* You don’t need one Route 53 per AZ.
* You configure **records once**, Route 53 directs based on routing policy.

✅ **Failover Example:**

* If one region goes down, Route 53 routes to another healthy region.

# 5 — Idempotency: what it is & how to implement

**Definition:** an operation that can be retried without changing the result beyond the first application.

**Why needed:** retries, network errors, at-least-once delivery semantics (SQS, HTTP retries) — prevents duplicate side-effects (double charges, duplicate DB rows).

**Patterns:**

* **Idempotency key**: client sends a key (UUID). Server stores key + result. Repeated calls with same key return same result.
* **Database upsert** with unique constraint on business key.
* **SQS FIFO deduplication**: message-deduplication ID or content-based deduplication.
* **Stateless idempotent endpoints**: GET or PUT semantics.

# 6 — Polling: short vs long polling (SQS context)

**Short polling**

* Immediately returns messages available at that moment; may return empty even if messages are in other servers.
* Less efficient for sparse queues.

**Long polling**

* SQS holds the connection open up to specified wait time (e.g., 20s) until a message arrives or timeout.
* Reduces empty responses, lowers API calls and cost, improves throughput and latency for consumers.

**When to use**

* Use **long polling** (recommended) for better efficiency and throughput, especially when message arrival is bursty or unpredictable.

# 7 — Amazon SQS vs other event systems (brief recap)

* **SQS**: reliable, simple queue — point-to-point asynchronous decoupling. Standard (high throughput, at-least-once) and FIFO (exactly-once ordering/dedup).
* **SNS**: pub/sub push to many subscribers (fan-out).
* **EventBridge**: event bus with routing rules, supports SaaS events and richer filtering and transformation.
* **Kafka**: distributed log/streaming platform (strong ordering, replay, partitioned topics, higher ops overhead).

# 8 — Decoupling microservices: why & patterns

**Why decouple?**

* Avoid blocking, isolate failures, scale components independently, make systems resilient to spikes.

**Patterns**

* **Queue** (SQS) between services for async processing.
* **Pub/Sub** (SNS) for notifications.
* **Event Sourcing / Streams** (Kinesis, Kafka) for high-volume streams and replayability.
* **Circuit Breakers, Backpressure** to prevent overload.

**Downsides of no decoupling**

* Tight coupling → single service failure cascades, synchronous waits slow user response, harder to scale.

# 9 — Handling very high SQS throughput — practical checklist & techniques

Goal: consume messages quickly and reliably at scale.

**1. Design & queue choice**

* Use **Standard queues** for high throughput; consider **FIFO** if ordering/strict dedupe needed (be mindful of throughput limits and message groups).

**2. Consumer scaling**

* **Autoscale consumers** (ECS/EKS tasks or EC2 ASG) based on `ApproximateNumberOfMessagesVisible` & `ApproximateAgeOfOldestMessage` metrics.
* For Lambda consumers, use **Lambda event source mapping** with `batchSize`, `maximumConcurrency` and **provisioned concurrency** if needed.

**3. Batching**

* Read and process messages in **batches** (up to 10 per ReceiveMessage). Process together and delete in batch.

**4. Long polling**

* Enable **long polling** (e.g., 20s) to reduce empty receives and improve throughput efficiency.

**5. Visibility timeout tuning**

* Make sure **visibility timeout** > time needed to process the batch; use heartbeats or extend visibility if processing takes longer.

**6. Parallelism / sharding**

* Increase parallel consumers; if order matters, use FIFO with **MessageGroupId** which enables parallelism across groups. Or shard into multiple queues for independent parallel processing.

**7. Dead-letter queues (DLQ)**

* Configure DLQ for poison messages; monitor DLQ and alert.

**8. Error handling & backoff**

* Exponential backoff on retry; avoid tight retry loops that overload consumers.

**9. Large payloads**

* Use **S3 payload offload** (SQS Extended Client) for messages > 256 KB.

**10. Monitoring & alarms**

* Key metrics: `ApproximateNumberOfMessagesVisible`, `ApproximateNumberOfMessagesNotVisible`, `ApproximateAgeOfOldestMessage`, `NumberOfMessagesDeleted`, `NumberOfMessagesReceived`.
* **CloudWatch Alarm** examples:

  * `ApproxAgeOfOldestMessage > X` → trigger scaling action.
  * `MessagesVisible > Y` → scale out consumers.
  * `MessagesSent / NumberOfMessagesDeleted` anomalies → alert.

**11. Throughput optimization**

* Tune consumers to utilize connection reuse, prefetching, efficient IO, parallel processing, and thread pools.

## 1. ☁️ Cloud Computing Basics

* **Definition**: On-demand delivery of IT resources (compute, storage, databases, networking, etc.) over the internet with pay-as-you-go pricing.
* **Models**:

  * **Public Cloud** → Fully hosted by provider (AWS, Azure, GCP).
  * **Private Cloud** → Dedicated for one organization (on-premises or hosted).
  * **Hybrid Cloud** → Combination of on-premises + cloud.
  * **Multi-Cloud** → Using multiple cloud providers together.

### Key Concepts

* **On-Demand** → Pay only when you use resources.
* **Auto-Scaling** → Increase/decrease resources automatically based on demand.
* **Elasticity** → Ability to expand/shrink resources quickly.
* **Difference**:

  * *Auto-Scaling*: Rules or policies trigger scaling.
  * *Elasticity*: Cloud’s inherent ability to expand or shrink instantly.

## 2. ⚙️ AWS Compute Services

### EC2 (Elastic Compute Cloud)

* Virtual machines on AWS.
* Choose instance types based on CPU, memory, storage, and networking.
* **Pricing models**:

  * *On-Demand*: Pay per use.
  * *Reserved*: 1–3 years commitment, cheaper.
  * *Spot*: Bidding unused capacity, very cheap, but can be interrupted.

### Lambda

* **Serverless compute** → runs code in response to events.
* Best for **small jobs, event-driven tasks** (image compression, notifications, serverless APIs).
* **Advantages**: No server management, pay per request, highly scalable.
* **Cautions**: Execution timeout, cold start latency, memory/CPU limits.

### Elastic Beanstalk

* **PaaS** (Platform as a Service).
* Developers just deploy code → AWS handles servers, scaling, load balancing, patching.
* Best for **web apps & APIs** with minimal infra management.

### ECS (Elastic Container Service) & EKS (Elastic Kubernetes Service)

* **ECS**: Run Docker containers on AWS.
* **EKS**: Managed Kubernetes clusters.
* Use for **microservices, containerized workloads**.

### Choosing Compute Option

* **EC2** → Full control, legacy apps, custom infra.
* **Lambda** → Event-driven, serverless, cost-effective.
* **Beanstalk** → Simplified deployment (web apps).
* **ECS/EKS** → Containerized apps, microservices at scale.

### DynamoDB

* Fully managed **NoSQL key-value & document DB**.

### Aurora

* AWS-developed high-performance relational DB.
* Compatible with MySQL & PostgreSQL.
* **5x faster than MySQL, 3x faster than PostgreSQL**.
* Use when you need **enterprise-grade relational DB performance**.
