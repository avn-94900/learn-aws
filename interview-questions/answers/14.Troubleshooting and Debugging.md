# 14.1 Compute Troubleshooting

## 1. How do you troubleshoot EC2 connectivity issues?

**Answer (structured approach):**

### Step 1: Check instance state

* Is EC2 running?
* Status checks passed?

---

### Step 2: Network-level checks

* Security Group → allows inbound (SSH 22 / HTTP 80)?
* NACL → not blocking traffic
* Route table → correct routing (IGW for public access)

---

### Step 3: Public access

* Has public IP / Elastic IP?
* Subnet is public?

---

### Step 4: OS-level issues

* SSH service running?
* Firewall (iptables) blocking?

---

### Step 5: Key pair / credentials

* Correct private key used?

---

### Step 6: Logs

* System logs (via EC2 console)

---

### Key insight:

90% of issues = **Security Group or wrong subnet**

---

### Challenge your assumption:

People blame AWS first → wrong
👉 Most issues are **misconfiguration**

---

## 2. How do you debug Lambda function errors?

**Answer:**

### Step 1: Check logs

* Amazon CloudWatch logs

---

### Step 2: Identify error type

* Timeout
* Memory issue
* Exception in code

---

### Step 3: Validate configuration

* Memory size
* Timeout setting
* Environment variables

---

### Step 4: Check dependencies

* Missing libraries?
* Wrong runtime?

---

### Step 5: Test manually

* Use test events

---

### Step 6: Use tracing

* AWS X-Ray

---

### Reality check:

Most Lambda failures =
👉 Timeout + external dependency slowness

---

# 14.2 Performance Troubleshooting

## 3. How do you investigate high latency in API Gateway?

**Answer:**

### Step 1: Identify where latency is

* API Gateway?
* Backend (Lambda / EC2)?

---

### Step 2: Use metrics

* CloudWatch:

  * Latency
  * Integration latency

---

### Step 3: Check backend

* Slow DB queries?
* Cold starts (Lambda)?

---

### Step 4: Enable caching

* API Gateway caching

---

### Step 5: Optimize payload

* Reduce response size

---

### Step 6: Use X-Ray tracing

* Trace full request path

---

### Critical thinking:

API Gateway is rarely the bottleneck
👉 Backend is usually slow

---

## 4. How do you troubleshoot SQS message processing delays?

**Answer:**

### Step 1: Check queue metrics

* Messages available
* Messages in flight

---

### Step 2: Consumer health

* Are workers running?
* Scaling properly?

---

### Step 3: Visibility timeout

* Too high → delays retries
* Too low → duplicate processing

---

### Step 4: Check DLQ

* Messages failing repeatedly?

---

### Step 5: Processing time

* Is consumer slow?

---

### Step 6: Scaling

* Increase consumers / concurrency

---

### Reality:

Queue delay ≠ SQS problem
👉 Usually consumer bottleneck

---

# 14.3 Infrastructure Troubleshooting

## 5. How do you identify and resolve security group misconfigurations?

**Answer:**

### Step 1: Check inbound rules

* Correct port open?
* Correct source (IP / SG)?

---

### Step 2: Check outbound rules

* Traffic allowed out?

---

### Step 3: Verify association

* Correct SG attached to resource?

---

### Step 4: Compare expected vs actual

* What should be allowed vs current config

---

### Step 5: Use logs/tools

* VPC Flow Logs

---

### Common mistake:

People open **0.0.0.0/0 for all ports**

👉 Works, but **huge security risk**

---

## 6. How do you diagnose RDS performance issues?

**Answer:**

### Step 1: Check metrics

* CPU utilization
* Memory
* IOPS
* Connections

(via CloudWatch)

---

### Step 2: Identify query issues

* Slow queries
* Missing indexes

---

### Step 3: Check connections

* Too many connections?

---

### Step 4: Storage bottleneck

* Disk I/O limits reached?

---

### Step 5: Enable insights

* Performance Insights

---

### Step 6: Scaling options

* Vertical scaling (bigger instance)
* Read replicas

---

### Critical thinking:

Most DB issues are NOT infrastructure

👉 They are:

* Bad queries
* Missing indexes
