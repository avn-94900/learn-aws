

# 13. Architecture and System Design (High-Value)

---

## 1. How would you design a highly available web application on AWS?

**Answer (typical architecture):**

* DNS → Amazon Route 53
* CDN → Amazon CloudFront
* Load Balancer → Application Load Balancer
* App Layer → EC2 / containers (multi-AZ)
* Database → RDS Multi-AZ
* Cache → Redis (ElastiCache)

---

### Key principles:

* Multi-AZ deployment
* Stateless app
* Auto Scaling
* Health checks

---

### Reality check:

“Multi-AZ = highly available” → incomplete
👉 If DB or app is single point → system still fails

---

## 2. How would you migrate an on-premises application to AWS?

**Answer (phased approach):**

### Step 1: Assess

* Dependencies
* Data size
* Downtime tolerance

---

### Step 2: Choose strategy (6 Rs)

* Rehost (lift & shift)
* Replatform
* Refactor

---

### Step 3: Migrate data

* DB replication
* Bulk transfer

---

### Step 4: Cutover

* Switch traffic gradually

---

### Challenge:

People assume lift-and-shift is enough
👉 It often leads to **high cost + poor performance**

---

## 3. What is Hybrid Cloud architecture?

**Answer:**

Hybrid cloud = **on-premises + cloud working together**

---

### Implementation:

* VPN or Direct Connect
* Shared identity (IAM/AD)
* Data sync

---

### Key AWS service:

AWS Direct Connect

---

### Trade-off:

* Flexibility vs complexity

---

## 4. Why keep some databases on-premises?

**Answer:**

* Compliance/legal restrictions
* Ultra-low latency needs
* Legacy system dependencies
* Data gravity (huge datasets)

---

### Challenge assumption:

“Cloud is always better” → wrong

👉 Sometimes:

* Migration cost > benefit

---

## 5. Latency challenges in hybrid systems

**Answer:**

* Network delay (internet/VPN)
* Bandwidth limits
* Unpredictable latency spikes

---

### Result:

* Slow APIs
* Timeout issues

---

## 6. How to handle latency in hybrid design?

**Answer:**

### Strategies:

* Caching (Redis, CDN)
* Async processing (queues)
* Data replication
* Minimize cross-network calls

---

### Critical thinking:

If your design depends on **real-time cross-network calls**, it will fail at scale

---

## 7. How would you design CI/CD for microservices?

**Answer:**

### Pipeline:

* Code → Build → Test → Deploy

---

### Tools:

* AWS CodePipeline
* AWS CodeBuild
* AWS CodeDeploy

---

### Flow:

* Each microservice → independent pipeline
* Docker images → pushed to ECR
* Deploy → ECS/EKS

---

### Mistake:

Single pipeline for all services → slows teams

---

## 8. How would you handle a sudden spike in traffic?

**Answer:**

### Immediate:

* Auto Scaling (EC2 / containers)
* Load balancing

---

### Preventive:

* CDN caching
* Queue buffering

---

### Advanced:

* Rate limiting
* Circuit breakers

---

### Reality:

Auto Scaling is NOT instant
👉 Cold start delay exists

---

## 9. Disaster recovery design for critical app

**Answer:**

* Multi-region setup
* Data replication
* Route 53 failover routing

---

### Strategy:

* Warm standby or active-active

---

### Key:

* Define RTO/RPO first

---

## 10. How would you secure sensitive data in AWS?

**Answer:**

### Data protection:

* Encryption at rest (KMS)
* Encryption in transit (TLS)

---

### Access control:

* IAM least privilege
* Role-based access

---

### Secrets:

* Secrets Manager

---

### Monitoring:

* CloudTrail + GuardDuty

---

### Weak assumption:

“Encryption = secure system” → wrong

👉 Misconfigured IAM = biggest risk

---

## 11. Serverless data processing pipeline design

**Answer:**

### Flow:

* Data ingest → S3
* Trigger → AWS Lambda
* Process → transform data
* Store → DB / S3 / analytics

---

### Add-ons:

* SQS (decoupling)
* Step Functions (workflow)

---

### Benefit:

* No server management
* Auto scaling

---

### Trade-off:

* Cold starts
* Execution limits

---

## 12. Blue-Green deployment (zero downtime)

**Answer:**

### Concept:

* Blue = current version
* Green = new version

---

### Steps:

1. Deploy new version (green)
2. Test it
3. Switch traffic using load balancer
4. Rollback if needed

---

### Tools:

* ALB
* CodeDeploy

---

### Mistake:

People skip testing → defeats purpose

---

## Final High-Level Insight (Very Important)

Most candidates give **tool-based answers**.

* Why multi-AZ vs multi-region?
* Why ECS vs EKS?
* Why sync vs async?

* Depends on synchronous calls everywhere
* Ignores cost

👉 It will fail in real world
